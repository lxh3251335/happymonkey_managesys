## V0.5 增补（合同台账与销售隔离）

- 数据字典：应用场景、城市（含区县别名，用于门店名称自动识别城市）改为系统管理中维护，改名同步到已有产品 / 项目，停用后不能新选。
- 我方签约主体：可维护多家签合同的公司（抬头、税号、法人、地址电话、开户行账号、默认主体）；报价选择签约主体时，报价单与合同打印其抬头与收款信息。
- 报价 → 合同：客户确认报价后“生成合同”，同时确认应收、门店写入合同号（可自动编号），合同为“拟定中”或“已签订”。也可手工新建合同（如框架合同）。
- 合同要素：签约主体、合同名称与内容、签订日期、签约金额（与门店订单合计的差额提示）、付款条款、履约期限、质保期与质保金、销售负责人、客户签约人、原件归档。
- 合同执行：开票（蓝字 / 红字冲销，开票合计不超过合同金额，错误登记可删除留痕）、到款（沿用合同回款分摊）、发货（门店）、实际成本（材料、人工、安装、运输、财务、其他），毛利优先按实际成本核算，否则按报价预估成本。
- 已签订合同的任何修改：非管理员提交变更申请（须填原因），管理员批准后生效；管理员直接修改须填原因；每次修改保存字段原值 / 新值、申请人、审批人和时间；合同详情汇总回款、开票、成本、附件等全部操作记录。非管理员不能把门店移入或移出已签订合同。
- 销售数据隔离：门店与合同有销售负责人；商务角色只看到和办理自己负责的门店、报价、合同、收款与经营数据；管理员可批量分配负责人。经营总览新增“销售业绩”维度。
- 报价 → 合同 → 执行 → 分析打通：经营总览按合同口径分析（有签约金额按签约金额分摊到门店与产品线、有实际成本按实际成本核算毛利、按签订月份归月、已终止合同不计入、只有合同记录的已签订合同单独计入），并显示合同执行概况（开票、开票未到款、实际成本、未归档、待审批，可点击进入合同台账对应筛选）；合同详情中可登记门店发货（记录发货日期，进入合同操作记录）；报价、门店与合同之间互相跳转。
- 合同台账快捷筛选（拟定中、待确认应收、有未收、已逾期、未开足票、开票未到款、未发完货、待审批变更、原件未归档）与客户、签约主体、业务线、城市、负责人、状态、签订月份筛选，合计随筛选变化；合同台账与开票记录支持 Excel 导出与导入（合同导入限管理员，记入变更记录）。

## V0.11 增补（报价与合同号）

- 合同号自动编号：沿用现有规律“前缀 + 年份 - 客户代码 - 序号”（如 TJ2026-SHHLZY-109），每个客户按年份各自连续编号；客户代码取客户资料中的“合同代码”，未填时从该客户已有合同号识别，都没有时退回通用格式 HT + 日期 + 序号。新建报价不再手填合同号，客户确认、生成合同时自动编号（可改）。
- 参考已签约项目：新建报价时可选一个已签合同的门店，带入其已确认报价的产品、数量和售价；业务员只能参考自己负责的门店，且不带成本。
- “已登记项目”只列出尚未签合同（或合同仍在拟定）的门店；合同已签订的门店新增报价版本属于合同变更，后端只允许管理层 / 系统管理员办理。
- 管理层角色补齐业务操作权限：可办理业务员的全部业务操作（门店、报价、合同、基础资料），仍不做财务登记与系统配置。
- 侧边栏菜单按使用频率调整：经营总览、项目台账、合同台账、客户报价、报价配置、基础资料、系统管理。

## V0.12 增补（报价跟进与客户报价模板）

- 报价跟进阶段：报价按“草稿 → 待客户确认 → 待生成合同 → 已转合同”流转，另有“未成交”和“已被新版本取代”。阶段由报价状态与门店合同状态共同决定（`QuoteStage`）；有合同号但没有确认动作的历史门店，其报价视为已转合同。
- 客户报价页默认只看“跟进中”（草稿 + 待客户确认 + 待生成合同），可按阶段、客户筛选；已转合同的仍可查，后续在合同台账、项目台账办理。
- 未成交：报价可标记未成交并填写原因，随时可恢复跟进（回到关闭前的状态）。客户已确认但未生成合同的报价标记未成交时撤销应收，恢复后需重新确认；已有回款或已生成合同的不允许。未成交报价不进入合同台账、经营分析、参考项目和标准配置推荐。
- 项目台账默认只看“已成交”门店（已有合同或客户已确认），另设“报价中（未签合同）”范围，用于先发货后补合同的门店。新登记且没有合同号的门店自动切到“报价中”。
- 客户报价模板：客户 × 项目类型一份，维护产品、数量与协议售价（不含成本）。新建报价时客户有启用的模板按模板带出，否则按项目类型标准配置带出。模板可从标准配置起草、从该客户最近报价带入，或在报价详情“存为客户报价模板”。管理员、管理层、业务员可维护。
- 原“报价模板”（抬头、收款信息与条款）改名为“报价单版式”，避免与客户报价模板混淆。

## V0.13 增补（应收口径与合同变更）

- 合同签订即有应收：门店所属合同为已签订 / 已完结（含只有合同号、没有合同记录的历史合同）时，其报价金额直接计入应收，不再需要逐份“确认应收”，也可以直接登记回款。合同拟定中、客户尚未确认的门店订单仍不计应收。
- 应收截止日期单独设置：没有截止日期的应收计入未收、不计逾期；合同台账新增“未设截止日”筛选，合同详情“设置应收截止日”为缺日期的门店补上。
- 确认并取代原报价：门店已有已确认报价时，新版本出具后通过“确认并取代 Vn”生效，原版本标记为“已被取代”（SUPERSEDED）并保留。合同已签订时属于合同变更，只有管理层 / 系统管理员可办理、必须填写原因，并记入合同变更记录；合同拟定中或没有合同时负责人可直接办理。新金额不得低于门店已到款；合同未填签约金额时，变更后的合同金额不得低于已开票金额。
- 合同依据固定：合同已签订的门店出新报价版本前，系统把现有生效的报价记为已确认，新版本在被确认取代之前不影响合同金额与应收。
- 回款按门店汇总：报价换版本后，旧版本名下登记的回款流水仍计入该门店。
- 批量设置应收截止日：合同台账合计行右侧的入口，对当前筛选结果中未设截止日的合同办理；可统一日期，或按“签订日期（没有则下单日期）/ 下单日期 + 天数”逐门店推算，只补缺、不改已有日期，缺基准日期的跳过并提示。
- 合同台账布局：顶部指标条并入表格上方随筛选变化的合计行，合同行压缩为两行，每页 20 条。
- 报价草稿可改可删：还没出具的草稿可以直接修改（明细整体替换、版本号不变）和删除；删除时可连带删除只为这份报价登记、没有其他报价、合同和发货记录的门店。已出具的报价不能修改也不能删除，只能复制为新版本或标记未成交。修改与删除均记入操作日志。
- 创建报价弹窗重排：门店、供应商与报价条件压成两行六列，明细行变矮、合计与备注各占一行，明细表按窗口高度自适应并在表内滚动，整窗一屏可见。

## V0.16 增补（粘贴识别与一对多登记）

- 物流粘贴识别：“发货物流”窗口顶部的粘贴框，从一段文字里拆出收货人、电话、地址、快递公司和运单号（`frontend/src/parsing/delivery.ts`，纯规则、在浏览器里完成）；没写快递公司时按单号开头推断并提示核对。项目台账“批量粘贴运单”：每行一个门店 + 运单号，按门店名称、项目编号或合同号对门店，核对后一起登记为已发货。
- 回款单（V16 `receipt_batch`）：银行到账的一笔钱可以分到同一客户的多份合同，每份合同的部分仍按原来的合同回款登记并分摊到门店；没分完的余额记为“待分配”，在回款流水页继续分。粘贴银行短信或回单文字可认出金额、日期、付款方、流水号并对到客户（`parsing/receipt.ts`）。
- 回款分配建议（`ReceiptAllocator`）：金额等于某张发票 → 那张发票的合同；等于某一份或某几份（最多 4 份）合同的未收之和 → 这几份；否则从最早到期的开始冲抵。只是建议，登记的人可以改。
- 发票登记（V17 `contract_invoice.group_id`）：一张发票可以分到多份合同，各行发票号码相同。上传电子发票 PDF 可读出号码、日期、价税合计、税率、类型、购买方和备注（`InvoiceParser`，用 PDFBox 读文字层）；备注里写了合同号的优先记到那些合同。原件自动存进各合同的附件（类别“发票”）。扫描件没有文字层，需手工填写。
- 写入前整体校验：回款和发票都先核对每一份合同（存在、不重复、不超过未收 / 未开票金额），任何一份不对整笔不登记。
- 前端识别规则有自动测试：`npm --prefix frontend run test:unit`（Node 自带的测试运行器，无新依赖）。
- 尚未做：回款凭证图片的保存与图片文字识别；工资分摊人工成本、税费公式；首页提醒与经营月报。

## V0.17 增补（企业微信机器人）

在企业微信里向机器人查询和录入。系统由本机主动连到企业微信（“智能机器人”的 API 模式、长连接），不需要公网地址，系统仍只在内网和 Tailscale 里。

- 模块划分：`bot` 包管“一条消息进来、回一段文字”，与聊天软件无关；`wecom` 包只管和企业微信的连接与收发格式。机器人不另写业务规则，调用的是网页用的同一批服务。
- 身份（V18 `bot_binding`、`bot_bind_code`）：每个人在“系统管理 → 账户安全”生成 8 位一次性绑定码（10 分钟有效），在和机器人的单聊里发“绑定 12345678”。之后机器人的每一步都以这个系统账号的身份执行：业务员只查得到自己负责的，成本和毛利只给能看成本的角色，操作日志记在本人名下。账号停用后机器人不再认。绑定码连错 5 次锁 10 分钟；发到群里的码当场作废。
- 查询：`应收`、`应收 客户名`、`逾期`、`合同 合同号或客户名`、`发货 门店名称`、`待发货`、`本月`、`帮助`。
- 录入（先回预览，对方回复“确认”才写入，“取消”放弃；预览在内存里保留 10 分钟）：
  - 运单：每行“门店名称 运单号”，对上门店的标记已发货，对不上的说明原因并跳过；
  - 收货信息：第一行门店名称，后面是收货人、电话、地址，只改认出来的内容；
  - 回款：银行到账短信或回单文字，认出金额、日期、付款方并对到客户，按 `ReceiptAllocator` 的建议分到合同；同一流水号不重复登记，同客户同日同额会提醒；
  - 发票：电子发票 PDF，认出后按建议分到合同，PDF 存进合同附件。
- 群聊：群里所有人都看得到回复，所以群里只办理发货相关的事，金额一律请对方单聊。群里要 @机器人 它才收得到。
- 连接配置（V18 `bot_config`）：系统管理员在“系统管理 → 企业微信机器人”填 Bot ID 和 Secret、启用或停用，并看连接状态和已绑定的人。Secret 只能写入，接口和日志都不返回；它以明文存在数据库里，数据备份里也有，备份文件要按密码对待。
- 连接行为：认证后每 30 秒一次心跳，连续两次没有应答即重连；断线按 1、2、4…30 秒的间隔重连。认证被拒绝、或被别处的新连接顶下线时不重连，在设置页显示原因，处理后点“重新连接”。同一个机器人同时只能有一处连接。
- 识别规则的两份实现：网页边输入边识别用 `frontend/src/parsing/*.ts`，机器人在服务端用 `DeliveryParser`、`ReceiptParser`。两边跑同一份用例 `shared/parsing/*.json`；改规则时先改用例，再同时改两处。
- 测试：`BotServiceTest`（绑定、按角色查询、各类录入）、`WecomSessionTest`（协议与文件解密）、`WecomConnectionTest`（对着本机的假服务端跑认证、心跳、重连）。
- 尚未做：还没有连过真实的企业微信机器人，回复里的加粗等格式、文件下载地址的实际表现要等真机联调；图片读不了（到账凭证截图要发文字）；每天定时推送逾期和待发货；随便怎么问都能懂（接大模型）；在机器人里改分配方式（要到网页上）。

## 当前限制

本版还没有公网地址（企业微信机器人由本机向外连接，不需要）；生产 PostgreSQL / Docker 验证等待可用环境。云智冷尚未对接（数据库保留关联 ID 字段，界面已不显示）。在线 Excel 导入、Excel 报价下载、发票核销、采购订单和供应商付款尚未实现。对客输出目前通过浏览器打印/PDF；合同为通用购销合同版式，甲方信息取自客户开票信息，后续可替换为公司合同模板。

当前用户角色为固定角色（系统管理员、管理层、财务、业务员、只读），已支持账户停用和密码重置；业务员按负责人隔离数据且看不到成本，其余角色查看全部。历史门店需管理员分配负责人后，对应销售才能看到。系统无客户门户，不应给外部客户分配内部只读账号。

## 建议下一阶段

### 业务确认与完整数据

核对历史项目、不同名称的同一门店、税口径和缺成本记录；补录客户实际回款。在“报价模板”中录入正式公司抬头、收款账户和报价条款；确认运输/安装等费用口径。为已签合同补传附件。

### 正式上线

在实际 PostgreSQL 上运行 CI 和业务回归；配置云服务器、域名与 HTTPS；完成备份恢复演练。补齐更细粒度授权；附件目录纳入备份；设计登录异常告警及审计留存。

### 规模与外部协同

实现服务端分页、索引和大数据量聚合；增加标准成本分项和审批流程；加入采购订单、供应商付款与发票核销。按云智冷正式 API 文档实现项目同步和异常处理；需要多企业 SaaS 时再引入明确的租户边界和集中会话。

每阶段按可验收的业务流程迭代，保留迁移与计算版本，避免直接覆盖历史报价或账务。
